# Final report structure

Use this exact structure and order. Fill every section. If a section is genuinely
empty, write "Nothing found — here is what I checked:" and list the checks. Never
delete a section.

---

```markdown
# Grill Report — <repo> @ <git short sha>, <branch>
**Level:** Senior · **Scope:** <full | area> · **Reviewed:** <n> files, <n> lines
**Verdict in one line:** <can this be trusted with real market data? yes / no / not yet, because X>

## Overall Score

**X.X / 10**

<Weighted arithmetic shown in one line. Then two or three sentences that do not
soften the number.>

## Category Scores

| Category             | Score | What it turns on |
| -------------------- | ----: | ---------------- |
| Architecture         |  X/10 | <one clause> |
| Frontend             |  X/10 | |
| Backend              |  X/10 | |
| FYERS Integration    |  X/10 | |
| Data Integrity       |  X/10 | |
| Technical Indicators |  X/10 | |
| Trading Signals      |  X/10 | |
| Security             |  X/10 | |
| Performance          |  X/10 | |
| Production Readiness |  X/10 | |

## Critical Problems

Most dangerous first. For each:

### 🔴 <Short title>
**Where:** `path/to/file.ts:LINE`
**What's wrong:** <the defect, stated as fact>
**How it fails:** <the concrete sequence: input/state → wrong output>
**What it costs:** <money, wrong price shown, credential exposed, crash, corruption>
**Confidence:** confirmed (read the code) | plausible (needs one check: <what>)

Repeat for every 🔴, then every 🟠. 🟡 and 🔵 go in a collapsed list at the end.

## Biggest Architectural Problems

<2–4 problems. For each: what the structure is, why it's wrong, what it will cost in
six months. Reference the specific boundary being violated.>

## Biggest Security Problems

<For each: the exact attack or exposure, the preconditions, and the consequence.
"An attacker who can X gets Y." If the answer is "requires local filesystem access on
a single-user machine," say so — calibrate, don't inflate.>

## Biggest Data Problems

<Anything that can put a wrong number on screen while looking correct. This is the
section the user should read first. Name the number, the source, and the failure.>

## Biggest Trading-Logic Problems

<Anything producing a misleading signal: look-ahead bias, insufficient history,
unvalidated thresholds, fabricated confidence. State explicitly which displayed
values claim more precision than the data supports.>

## Performance Risks

<What breaks first, and at what number. Table form:>

| Load | What happens | First thing to break |
|---|---|---|
| 50 symbols | | |
| 500 symbols | | |
| 5,000 symbols | | |
| 1,000 ticks/sec | | |
| 2 dashboards open | | |

## Dead Code, Duplication, and Debt

<Files that are unreachable. Logic implemented twice. Where the two copies disagree —
and disagreement is a correctness finding, not a cleanliness one.>

## Testing Gaps

<What is untested that matters most, ranked. Call out any test whose fixtures were
generated by the code under test.>

## Top 10 Fixes

In priority order. Exactly this format for each:

**1. <title>**
- **Priority:** 🔴 CRITICAL
- **Problem:** <one sentence>
- **Why it matters:** <the consequence in money / trust / uptime terms>
- **Recommended solution:** <specific, implementable — name the approach, not "improve X">
- **Files affected:** `path/a.ts`, `path/b.tsx`
- **Effort:** S | M | L

## What I Could Not Verify

<Honest list: things you'd need to run, credentials you don't have, behavior only
observable against the live market. Do not pad the findings with guesses — put them
here instead.>

## What's Actually Good

<Only genuinely non-obvious things you verified. One line each. Three items maximum.
If there are none, write "Nothing that rises above baseline competence." and move on.
Do not manufacture entries to soften the report.>

---

**Grilling starts now.** <Then ask question 1 — one question, then stop.>
```
